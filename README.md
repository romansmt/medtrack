# MedTrack

**A simulated Austrian health & pharmacy platform** — medication availability search, pharmacy discovery, price comparison, and adherence tracking, behind a REST API built with a clean, hexagonal architecture.

> **Portfolio / study project — no real data, ever.** MedTrack simulates the shape of real Austrian systems (the e-card, ELGA e-Medikation, ID Austria login) strictly for learning and demonstration. Every patient, prescription, pharmacy, and stock number is fake and generated by the application itself — no real personal, medical, or government data is used or requested anywhere in this project.

## What is this?

MedTrack started as a simulation of the Austrian public health insurer's (ÖGK) e-prescription lookup, then grew into a fuller pharmacy companion by combining the functionality of two real Austrian apps — **ApoScout** (medication availability and pharmacy search) and **ApoApp** (a broader health companion with adherence tracking). The result is a single backend that models:

- Looking up your own e-prescriptions, the way ELGA's e-Medikation would
- Searching for a medication and instantly seeing which nearby pharmacies have it in stock
- Finding an open — or emergency-duty ("Bereitschaftsdienst") — pharmacy near you, at any hour
- Comparing what a medication costs across different pharmacies
- Keeping a personal list of favorite pharmacies and medications, and reserving stock ahead of a visit
- Tracking a daily medication schedule and confirming or skipping each dose, the way a real adherence app would

It's built the way a production health system would be — with an explicit boundary between business logic and the (currently mocked) integrations it will eventually plug into — while treating the fake data exactly as sensitively as if it were real, since that discipline is itself the point of the exercise.

## Features

| Area | What it does |
|---|---|
| **Prescriptions** | Look up a patient's e-prescriptions by insurance number (SVNR), mirroring ELGA e-Medikation |
| **Drug catalog** | Search medications by name, active substance, or PZN (pharmaceutical registry number); view a simulated package leaflet |
| **Availability check** | Check a whole "selection list" of medications against every nearby pharmacy at once — in stock, out of stock, or not carried |
| **Pharmacy locator** | Find pharmacies by distance, see full opening hours, and find who's on emergency/night duty right now |
| **Pricing & comparison** | Models both the fixed prescription co-payment (Rezeptgebühr) and variable OTC pricing, and ranks pharmacies cheapest-first per medication |
| **Favorites** | Bookmark pharmacies and medications for one-tap access later |
| **Reservations** | Reserve a medication at a specific pharmacy, with pharmacies able to opt out of the feature entirely |
| **Medication plan** | Track a daily dosing schedule per medication (including multiple times a day) and confirm or skip each dose — adherence history included |

A live per-pharmacy stock feed is simulated by a scheduled background job that periodically nudges inventory, so the data doesn't feel frozen in time. Location search is backed by a **real** integration with the public OpenStreetMap/Nominatim geocoding API, not a mock.

## Architecture

Layered / hexagonal (ports & adapters), so every simulated integration — pharmacy stock, geolocation, the e-card — sits behind an interface a real integration could later be swapped in behind, without touching business logic:

```
Presentation   → REST controllers (Spring MVC), OpenAPI/Swagger docs
Application    → services (use cases) + ports (integration interfaces)
Infrastructure → adapters implementing those ports (JPA repositories, the mock e-card, the real geocoding client)
Domain         → the core model — Patient, Prescription, Pharmacy, Drug, Reservation, MedicationSchedule, …
```

## Tech stack

- **Java 21** / **Spring Boot 3** — REST API, dependency injection, scheduling
- **PostgreSQL** + **Flyway** — versioned, additive schema migrations (8 and counting)
- **springdoc-openapi** — interactive Swagger UI generated straight from the code
- **JUnit 5**, **Mockito**, **AssertJ**, **Testcontainers** — unit tests for business logic, real-Postgres integration tests for the full HTTP-to-database path
- **Docker Compose** — one-command local Postgres for development

## Project status

The backend is complete and tested: prescriptions, drug catalog, availability, pharmacy locator, pricing/comparison, favorites/reservations, and medication-adherence tracking are all implemented, migrated, and covered by an automated test suite. A React frontend is the next milestone — see [docs/TASKS.md](docs/TASKS.md) for the live backlog and [docs/PROGRESS.md](docs/PROGRESS.md) for a task-by-task write-up of what was built and why.

## Getting started

```bash
docker-compose up -d
mvn spring-boot:run
```

Health check: `GET http://localhost:8080/actuator/health` should return `200`. Once running, explore the full API at `http://localhost:8080/swagger-ui/index.html`.

```bash
mvn verify
```

Runs the full automated test suite (spins up its own throwaway Postgres via Testcontainers, so `docker-compose up` isn't required just to test).

If `mvn`/`java` aren't on your PATH, or you hit a database connection error, see [docs/DEVELOPMENT.md](docs/DEVELOPMENT.md) — it also has copy-pasteable verification commands for every feature area.
